# Hospital Management System — Phase 1 Business Logic Specification

This document describes what the system must actually *do*, beyond CRUD create/read/update/delete on each entity. JDL generates the scaffolding; everything below is logic that has to be written deliberately in the service layer. Organized by flow area, in the order a real patient encounter moves through them.

## Registration and duplicate handling

When Reception registers a new patient, before the record saves, the system must run two separate checks. First, if a national ID, passport, or birth certificate number was entered, it checks for an exact match against existing patients — if found, Reception is shown the existing record and must explicitly choose to use it or confirm creating a new one anyway. Second, regardless of whether an ID was entered, the system runs a softer "possible duplicate" check based on name, date of birth or age, and phone number — this never blocks the save, it simply surfaces potential matches for Reception to review, since many patients (minors, unidentified emergency cases, people without documents) won't have an ID to check against in the first place.

Separately, when a Nurse or Doctor creates a patient through the emergency-intake path (unconscious or unidentified patient, or a minor who can't provide guardian information), the system must generate a temporary ID in the non-sequential format described in the domain doc, mark the record's registration status as incomplete, and immediately allow a Visit to be created and clinical work to begin — registration completeness is not a precondition for treatment in this path. Later, when a Reception or Super Admin user runs the merge action to connect an incomplete record to a confirmed real one, every piece of clinical data already attached to the temporary record (vitals, orders, results, prescriptions) must be reassigned to point at the real patient record, and the temporary record's status changes to merged rather than being deleted.

## Appointments and check-in

An appointment on its own never creates a Visit or places anyone in a queue — it only becomes operationally real when Reception performs an explicit check-in action at the time the patient physically arrives, which is the point where a new Visit gets created and the appointment's own status moves from scheduled to checked-in. If a patient never shows up, the appointment eventually becomes a no-show and stays that way permanently; if that same patient arrives later anyway, Reception treats them as an ordinary walk-in and a brand new, entirely unrelated Visit is created — there must be no code path that tries to retroactively link a late arrival back to a missed appointment.

## The Visit as the central state machine

Every Visit carries its own status that represents the big picture of where the patient is in their encounter, but this status is not something other parts of the system set directly except at a few specific trigger points — for the most part it should be computed. When a Nurse submits vitals, the Visit moves itself into the doctor's queue. When a Doctor completes a consultation, the system must inspect what was actually ordered or prescribed during that consultation and decide the next state accordingly: if nothing is pending, the Visit can move straight toward payment; if a lab or radiology order exists, the Visit needs to reflect that something is still outstanding; if a prescription exists, the same applies. Critically, a Visit can have more than one of these pending at once — a doctor ordering a blood test and writing a prescription in the same consultation is normal — so the system cannot represent this as a single linear status value. Instead, the correct approach is for the Visit to periodically (or event-drivenly, whenever a linked Order or Prescription changes status) check whether every Order and Prescription attached to it has reached a resolved state, and only once that condition is fully true does the Visit itself advance to the payment-waiting stage. This check needs to run every time an Order's result is entered or a Prescription's payment/dispense status changes, since either of those events could be the last outstanding item that unblocks the Visit.

Priority on a Visit is not purely decorative — it determines sort order in the queue screens, but selection from that queue is never restricted to whatever sorts to the top; any queued Visit must remain selectable by staff, with an optional reason field if they pick something out of order.

## Consultation billing timing

A consultation's charge should not wait until the very end of the visit to exist — the moment a Doctor marks a Consultation as completed, the system should generate the corresponding bill line item for the consultation fee immediately, pulling its price from the Service catalogue entry for general consultation. Lab, radiology, and pharmacy charges work the same way, each generating their own bill line item at the point their respective Order or Prescription resolves, rather than everything being assembled in one pass at the end. The Bill as a whole is only considered finalized and ready for Finance to actually collect against once the Visit itself reaches the payment-waiting stage — at that point all the incrementally-generated line items are summed into the total the patient actually pays.

## Referral's effect on the encounter

Creating a Referral is not simply logging a record — it is a decision that the patient's local clinical journey for this visit has ended. When a Doctor creates a referral, the system should treat this the same way it treats "nothing further is pending": rather than continuing to wait for orders that were never placed, the Visit should move toward the payment stage based on whatever was actually completed up to that point (typically just the consultation fee, plus any lab or radiology that had already resolved before the referral decision was made). The Referral record itself, and the ability to generate and optionally email its PDF, exists independently of this billing effect — one is about transferring clinical information to wherever the patient is going, the other is about correctly closing out what this hospital is owed for what it actually did.

## Stock reservation and the payment-before-dispense guarantee

Prescribing a drug does not immediately reduce the pharmacy's actual stock count. Instead, the system must track a separate reserved quantity against that drug, and the figure that matters for checking whether a new prescription can even be placed is the available quantity, calculated as current stock minus everything currently reserved. This reservation is what allows Finance to bill confidently — by the time a Visit reaches the payment stage, every prescribed item on it has already been confirmed as genuinely available, because the stock was set aside the moment it was prescribed, not merely checked and forgotten. Only when Pharmacy actually hands over the medication does the real stock quantity decrease and the reservation against it clear. Because dispensing is gated behind payment, a Prescription's own status needs to reflect this transition explicitly — once the Bill it belongs to is paid, the Prescription should move into a state that signals to Pharmacy's dispensing queue that it is now safe to hand over, without Pharmacy needing to separately check the Visit or Bill's own status to know this. This applies identically whether the prescription came from a normal consultation or from a walk-in pharmacy-only visit, though the walk-in path additionally requires payment to happen before any clinical consultation exists at all, since there is no doctor or visit driving the sequence in that case.

## Vitals validation

Every numeric vital sign entered by a Nurse needs to be checked against two different thresholds, not one. The first threshold catches values that are outside a normal healthy range but still biologically possible — these should be saved, but the system should surface a visible warning so the Nurse is aware the reading looks concerning. The second, wider threshold catches values that are not physiologically possible for a living person — these must be rejected outright and cannot be saved, since a value like that almost certainly represents a data entry mistake rather than a real reading. These two behaviors need to be genuinely distinct in the code, not collapsed into a single generic validation error, because one is informational and one is a hard block.

## Corrections and audit discipline

Two different correction patterns exist in this system and they must not be mixed up. For Patient records and Vitals entries, a correction is an edit-in-place that requires a reason to be supplied, with the previous value retained in a history log rather than simply overwritten — the current value is still the single source of truth for that field, but the change is fully traceable. For Consultation notes specifically, once a Visit has progressed past the point where that consultation was recorded (meaning the visit has moved toward payment, results have come back, or anything else has advanced), any further change must not overwrite the original entry at all — it must be recorded as a new, separate addendum note that is clearly linked to the original but leaves it completely untouched. Applying edit-in-place logic to a Consultation after this point, or applying addendum-only logic to something like a Patient's phone number, would both be implementation mistakes relative to what was actually decided.

## Role-based access enforcement

Every endpoint's authorization needs to reflect the specific, narrow rules that were locked for each role, not a blanket "this role can access this entity" check. A Lab user should only ever be able to see Orders of type lab, never radiology orders, and the patient information visible to them should be limited to identifying details, not the full clinical record. Finance should be able to see enough about an Order or Prescription to generate a bill line item — a test name and its price — but not the clinical notes or diagnosis attached to the same visit. A Doctor should see their own queue and their own patients' full records, but has no access to billing actions or user management. These distinctions need to be enforced in the service or controller layer on a per-endpoint basis, because a generic role check alone will not correctly express them.

## Outpatient to inpatient conversion

When a Doctor uses the admit-patient action during or after a consultation, the underlying Visit record does not close and get replaced by a new one — its type field changes in place from outpatient to admission, and everything already recorded against that Visit (vitals, the consultation itself, any orders already placed) remains attached and intact. This action deliberately bypasses the normal outpatient path toward payment and closure, since an admitted patient's billing will instead accumulate over the length of their stay under the rules that will be defined when the inpatient domain itself is designed. For Phase 1 purposes, the conversion action itself and the type change need to exist and work correctly, even though the full behavior of what happens next as an admitted patient is not yet built.
